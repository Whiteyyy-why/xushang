# 大仓库优化 · 0.2

## 用户可见的变化

| 操作 | 新行为 |
|---|---|
| 保存现场 | 笔记先写入并同步到磁盘，再排队检查文件 |
| 打开现场 | 先返回本地笔记与摘要；不等待 Git |
| 检查范围 | 默认 Git 改动 + 关注文件，可限定文件/目录 |
| 未跟踪项 | 默认不遍历；可显式纳入，未展开目录标记为部分覆盖 |
| 停止检查 | 取消当前任务；Windows 同时终止所属 Git 进程树 |
| Git 失败/超时 | 保留已采集内容并标记部分完成，不回退遍历全目录 |
| 历史 | 首次加载 100 条，更早记录按需加载 |
| 存储 | 增量追加日志，不随每条笔记重写所有旧快照 |

~~~mermaid
flowchart LR
  A[点击保存] --> B[追加笔记并同步磁盘]
  B --> C[返回保存成功]
  B --> D[后台队列]
  D --> E[优先采集指定文件]
  E --> F[在预算内检查 Git 与范围内文件]
  F --> G{完成情况}
  G --> H[完整或部分完成]
  G --> I[取消 / 失败 / 中断]
  H --> J[追加本次文件摘要]
  I --> K[保留笔记并显示真实状态]
~~~

文件摘要在后台实际采集，界面显示采集时间。它不是“点击保存那一瞬间”的原子源码快照，也不能用于源码回滚。

## 资源边界

- 后台任务串行执行，避免多个项目同时争抢磁盘。
- Git 输出边读边处理：每个命令最多 5,000 条记录、512KB 输出；达到限制终止读取。
- 5 秒为检查时间预算，到时发出终止；系统 I/O 和进程回收可能额外耗时。
- 文件内容读取保持单文件 2MB、单次 64MB 的限制；明确标记未比较的范围。
- Git 默认不枚举未跟踪文件；普通目录使用流式目录迭代器。
- 缓存保留最近 8 个项目，60 秒内复用。
- 取消和重启不会把未完成的文件检查当成成功。
- 完整历史仍保存在磁盘并在启动时重放。极长历史或大量全量快照的冷启动，仍有进一步优化空间。

## 数据迁移与恢复

旧版 data.json 和 data.json.bak 保留。首次启动新版创建 checkpoint.json / checkpoint.json.bak，后续事务追加到 journal.ndjson。

每条事务包含递增序号与校验值，并在返回保存成功前同步磁盘。启动时重放完整事务：
- 不完整的末尾片段保留到 journal.ndjson.partial，恢复到最后一条完整事务。
- 完整事务校验失败时停止加载，不静默丢弃记录。
- 备份中的 pending 检查恢复为 interrupted，避免无限排队。
- JSON 导入导出仍兼容版本 1 的记录格式，新增字段记录状态和范围。

## 实测方法与结果

基准使用真实的 **100,000 个受跟踪文件、20,000 个未跟踪文件、100 条历史**。

为避免压测准备阶段生成海量无意义的 Git 对象，使用相同文件内容与 Git 官方的批量索引接口建立真实索引和提交；索引的 stat 缓存为冷状态。方法依据：[git-update-index 官方文档](https://git-scm.com/docs/git-update-index#_using_index_info)。应用本身不会修改用户的 Git 索引或配置。

| 指标 | 本机结果 |
|---|---:|
| 保存笔记接口中位数（5 次） | 7 ms |
| 保存笔记接口最大值（5 次） | 16 ms |
| 项目列表 + 详情中位数（20 次） | 31 ms |
| 项目列表 + 详情 P95 | 32 ms |
| 服务重启 | 7 ms |
| 保存响应前本次日志追加量最大值 | 598 bytes |
| 默认范围的冷检查 | 5,611 ms，部分完成 |
| 限定一个关注文件后的后台检查 | 1,567 ms，完成 |
| 分支变化识别 | 通过 |

**该结果证明保存和打开不会等待大仓库扫描，不代表已经全量扫描十万个文件。** 保存耗时测量使用明确的单文件范围，未跟踪枚举关闭；默认范围测试保留了超时的真实结果。

原始记录：performance-large.json。重测：npm run benchmark。脚本只创建和清理 test-results 内的独立合成目录。
